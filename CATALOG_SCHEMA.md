# Схема каталога упражнений (exercise_library.json)

`exercise_library.json` — источник истины. `EXERCISE_LIBRARY.md` — читаемая
проекция для людей, обновляется вручную или генерируется из json (решить в
Claude Code, лучше генерировать, чтобы не рассинхронивались).

## Обязательные поля при добавлении нового упражнения

| Поле | Тип | Допустимые значения | Валидация |
|---|---|---|---|
| `code` | string | уникальный snake_case | не должен повторяться в каталоге |
| `name` | string | любое | — |
| `equipment` | string \| null | `board`, `pull_buoy`, `board_optional`, ... или `null` | `null` = без инвентаря |
| `volume_unit_m` | int | `50` или `100` | **обязательно**: `equipment != null` → `volume_unit_m == 100`; `equipment == null` → `volume_unit_m == 50`. Это прямое следствие правила из PLAN_RULES.md ("Правило кратности объёма") — приложение должно проверять это при сохранении новой записи, а не доверять ручному вводу. |
| `tier` | string | `base`, `medium`, `advanced` | новое упражнение по умолчанию не `base`, если явно не решено иначе |
| `status` | string | `mastered`, `in_progress`, `proposed`, `deferred` | новое упражнение начинается как `proposed` |
| `focus` | string | короткая фраза | обязательно непустое — без фокуса упражнение бесполезно в выводе плана |
| `notes` | string | опционально | причины исключения фиксировать здесь с пометкой "организационная"/"техническая" (см. PLAN_RULES.md) |
| `always_include` | bool | `true`/`false` | **добавлено 2026-09-16, уточнено в тот же день.** `true` (по умолчанию) — упражнение включается в план каждый раз, когда доступно. `false` — упражнение случайно (монетка ~50/50 при каждой генерации, `Math.random()`, не история журнала — так было в первой версии, оказалось мало вариативности) то включается в план, то нет (см. PLAN_RULES.md "Разнообразие"). Применяется только к `status: mastered`/`in_progress` — у `proposed` своя логика (не более 1 нового упражнения за тренировку, выбор тоже случайный из всех подходящих кандидатов), `always_include` на них не влияет. |
| `requires` | string \| null | код другого упражнения в каталоге, или `null` | **добавлено 2026-09-22.** Для упражнений, которые имеют смысл только после того, как освоен предыдущий шаг прогрессии (например пятишаговая прогрессия кроля на спине — каждый шаг требует предыдущий). Пока `requires` не `null` и статус упражнения по этому коду не `mastered`/`in_progress`, генератор не предложит это упражнение сам как "новое" в этой тренировке (случайный выбор из `proposed`-кандидатов его пропускает) — но ручное включение через оверрайд (`forceInclude`/чек-лист) по-прежнему работает, это осознанное решение тренера. Валидация: если указано, код должен существовать в каталоге. |

## Правило перехода статусов

```
proposed → in_progress → mastered
proposed → deferred (если "сложно" по технической причине)
deferred → proposed (через 1-2 тренировки, для повторной попытки)
mastered → deferred (не должно происходить по организационной причине —
           см. PLAN_RULES.md "Причины исключения")
```

Приложению не обязательно жёстко enforce-ить эти переходы кодом на старте,
но генератор плана должен читать `status`, чтобы не предлагать
`deferred` упражнения раньше, чем через 1-2 тренировки после последней
попытки (для этого понадобится метка даты последней попытки — сейчас в
схеме её нет, добавить поле `last_attempt_date`, когда появится журнал
тренировок, см. SWIMMER_PROFILE.md).

## Если поле добавляется в будущем

При любом новом поле в схеме — обновить всех уже существующих упражнений
в `exercise_library.json` (например через дефолтное значение), а не
оставлять null/missing у старых записей: генератор не должен падать или
угадывать на отсутствующих полях.
