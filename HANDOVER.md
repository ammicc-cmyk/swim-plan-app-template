# Handover: Генератор планов плавательных тренировок

> **Это отдельное развёртывание того же приложения**, с нейтральным
> каталогом упражнений (см. SWIMMER_PROFILE.md — заполните под своего
> пловца) и пустым журналом. Остальной текст ниже — техническая
> документация и история решений по правилам генератора из исходного
> проекта; упоминания конкретной пловчихи и её прогресса ниже относятся
> к оригинальному развёртыванию, не к этому каталогу (он уже сброшен).

## Контекст

Планы тренировок для пловчихи (43 года, начала заниматься ~1.5 месяца назад,
бассейн 50 м без разделителя на 25 м) собирались вручную в диалоге с Claude
на протяжении нескольких тренировок. Логика построения плана уже
стабилизировалась — задача этого проекта: закодировать эту логику в
приложение, а не изобретать новую.

**Важно:** вся логика ниже — детерминированная (rules-based), не творческая.
AI не обязателен для генерации плана. См. раздел "AI vs rules engine" в конце.

## Текущее состояние пловчихи (на момент handover)

- Проплывает 50 м без остановки, но медленно
- Освоено и хорошо идёт: catch-up drill, fist drill, ноги с доской (кроль),
  билатеральное дыхание (3-3), одной рукой с колобашкой (single-arm)
- Не пошло с первой попытки: zipper drill, скаллинг — слишком тонкая
  координация, отложено, не убрано насовсем
- Брасс-ноги были исключены на одной тренировке не по техническим причинам,
  а потому что инвентарь физически лежал не на той стороне бассейна —
  организационная причина, не техническая. Не путать эти два типа причин
  исключения упражнения в логике приложения (см. `PLAN_RULES.md`, раздел
  "Причины исключения").
- Резерв-упражнение в конце тренировки выполняется стабильно —
  кандидат на перевод из опционального в обязательный объём.

Полная история тренировок и решений — `SWIMMER_PROFILE.md`.

## Ключевые бизнес-правила (кратко, детали в PLAN_RULES.md)

1. Весь инвентарь лежит на **стартовой стороне** бассейна.
2. Упражнение с инвентарём должно начинаться и заканчиваться у старта →
   объём кратен **100 м** (туда-обратно), либо 2×100 м.
3. Упражнения без инвентаря — кратны **50 м**.
4. Отдых — после **каждых 50 м**, не после каждого упражнения.
5. Порядок блоков: **сначала всё с инвентарём, потом всё без** —
   не чередовать, иначе инвентарь остаётся на дальнем бортике.
6. Новое/непривычное упражнение — первая попытка уменьшённым объёмом
   (1×50 вместо стандартного), кроме случаев, когда пользователь явно
   задаёт полный объём.
7. Резервное упражнение в конце — опционально, тот же стиль/фокус,
   что и кроль в полной координации (для сравнимости прогресса), не новое упражнение.
8. Заминка — всегда последний пункт, свободный стиль, спокойный темп.

## Открытые вопросы для следующей итерации

- Перевести резерв из опционального в обязательный объём — зависит от
  причины исключения брасс-ног (если это была усталость к концу
  тренировки — не переводить).
- Нужна ли пользователю прогрессия по неделям (не только план на одну
  тренировку), т.е. авто-наращивание объёма/сложности со временем.
- Формат ввода: ручной (тренер заполняет профиль пловца) или интерактивный
  опрос перед генерацией.

## Расширяемость каталога

Пользователь планирует регулярно добавлять новые упражнения. Источник
истины для каталога — `exercise_library.json` (не markdown-таблица,
она может устаревать). Схема полей и правила валидации при добавлении
нового упражнения — `CATALOG_SCHEMA.md`. Приложение должно:

1. Загружать каталог из json, а не хардкодить упражнения в коде генератора.
2. При добавлении нового упражнения — форма/интерфейс, который проверяет
   обязательные поля из `CATALOG_SCHEMA.md` (особенно связку
   `equipment` ↔ `volume_unit_m`, это прямое следствие правила кратности
   объёма из `PLAN_RULES.md`).
3. `EXERCISE_LIBRARY.md` можно either генерировать из json при сборке
   (рекомендуется), either держать вручную — но тогда он рискует
   разойтись с json и не должен использоваться кодом как источник данных.

## Что нужно от Claude Code

1. Прочитать `PLAN_RULES.md`, `exercise_library.json` и `CATALOG_SCHEMA.md`
   — это источник истины для логики генератора, не переизобретать правила.
2. Решить архитектуру (rules engine vs AI vs гибрид) — см. раздел ниже.
3. Спроектировать модель данных: профиль пловца, история тренировок,
   каталог упражнений, ограничения (инвентарь/без инвентаря, кратность).
4. Генератор должен уметь: (а) собрать план с нуля по правилам,
   (б) корректировать план по фидбэку («слишком сложно», «убрать
   упражнение», «сделать больше объёма») — это основной сценарий
   использования, который проявился в диалоге.

## AI vs rules engine — что решить в самом начале

**Вариант A — чистый rules engine (рекомендуется как основа).**
Каталог упражнений (`EXERCISE_LIBRARY.md`) + правила (`PLAN_RULES.md`) →
алгоритм собирает план: блок с инвентарём → блок без → резерв. Никакого
обращения к LLM в рантайме не нужно. Плюсы: предсказуемо, бесплатно в
эксплуатации, не требует ключей/аккаунтов, можно сделать статическим
сайтом (чистый JS/HTML, без бэкенда).

**Вариант B — AI-генерация поверх каталога.**
Используется, если нужна гибкая реакция на произвольный текстовый фидбэк
("слишком сложно", "хочу больше вариативности") без жёсткого прописывания
всех веток в коде. Требует вызова Anthropic API (Claude) из приложения —
это отдельный API-ключ с отдельным биллингом, **не связан с аккаунтом
Claude Code**, который используется только на этапе разработки, не в
собранном приложении.

**Вариант C — гибрид.** Rules engine собирает базовый план, AI используется
только для обработки свободного текстового фидбэка тренера
("сложно", "хочу другое упражнение сюда") — конвертирует фразу в
структурированную команду для rules engine. Дешевле и предсказуемее
варианта B при сохранении гибкости диалога.

Предполагаю: для этого конкретного кейса подходит Вариант A или C —
диалог показывает, что вся логика уже укладывается в правила, а не в
открытую креативность.

## Реализация (2026-09-16)

Выбран **Вариант A** — чистый rules engine, без AI в рантайме
(`js/rulesEngine.js`). Собрано статическое веб-приложение: `index.html` +
`css/styles.css` + `js/*.js` (ES-модули).

**Хранение данных.** localStorage + ручной экспорт/импорт JSON (обсуждали
компромисс с пользователем перед реализацией). При первом запуске каталог
и журнал загружаются из встроенных `<script type="application/json">` в
`index.html` (копии `exercise_library.json` / `training_log.json` —
нужны, чтобы страница работала при открытии из `file://`, без fetch).
После первого запуска приложение работает с localStorage. Кнопки
«Экспорт»/«Импорт» на вкладках «Каталог» и «Журнал» — способ вручную
синхронизировать localStorage с файлами на диске; `exercise_library.json`
остаётся источником истины только в том смысле, что именно он вручную
экспортируется/коммитится, а не автообновляется.

**Как запускать.** Открывать `index.html` напрямую двойным кликом
**не работает** в Chrome/Edge — они блокируют ES-модули (`import`/`export`
в `js/main.js`) при загрузке через `file://` (CORS). Нужен любой локальный
статический сервер из папки проекта, например `npx serve` или
`python -m http.server`, затем открыть `http://localhost:<порт>/`. Это не
бэкенд в смысле логики приложения — сервер просто раздаёт файлы.

**Формат вывода плана.** Закреплено в PLAN_RULES.md: сначала краткий
нумерованный план, потом подробности по каждому пункту (пример дал
пользователь — тренировка №15 с порогом).

**Разминка и порядок блоков (исправлено 2026-09-16).** Первая версия
ставила разминку (1×50м) перед блоком с инвентарём, ориентируясь на
порядок в SWIMMER_PROFILE.md (тренировка N). Пользователь указал на
физическую ошибку: бассейн 50м без разделителя, весь инвентарь на
старте — после разминки в 1×50м пловчиха оказывается на дальнем борту,
где инвентаря нет. Исправлено: блок с инвентарём теперь строго первый
пункт плана (объём до него = 0), разминка — первый пункт блока без
инвентаря сразу после. Правило записано в PLAN_RULES.md, раздел
"Позиция у борта". См. `js/rulesEngine.js`.

**Итог тренировки кратен 100 м (исправлено 2026-09-16).** Первое
исправление позиции у борта решало только доступ к инвентарю, но
пользователь указал на более общее правило: весь план "живёт" у старта —
пловчиха должна не только начинать, но и заканчивать тренировку там же.
Значит суммарный обязательный объём (без резерва) обязан быть кратен
100 м, а не просто лежать в диапазоне 700–900 (850 не годится, 800/900 —
годятся). Записано в PLAN_RULES.md ("Позиция у борта"). В генераторе
(`js/rulesEngine.js`) объём основного блока кроля (`ne_main_crawl`)
теперь подбирается с учётом чётности остального объёма, чтобы итог
всегда получался кратным 100; подрезка при переполнении диапазона тоже
это учитывает. Правило допускает собирать один круг 100 м из двух
**разных** упражнений по 50 м (пример от пользователя: "50м кроль на
кулаках + 50м обычный кроль") — это ещё не реализовано в UI как единая
строка плана, генератор просто гарантирует кратность 100 на уровне
итоговой суммы.

**Каждый пункт плана кратен 100 м, не только итог (исправлено 2026-09-16,
второй раунд).** Первое исправление проверяло только суммарную кратность
100 у всей тренировки — этого оказалось недостаточно: генератор всё ещё
мог вставить одиночный пункт 50 м (разминка/брасс/спина/заминка)
посередине плана, из-за чего следующий пункт стартовал не со старта
(конкретный пример: «Catch-up drill» на шаге 8 начинался с финиша).
Настоящая причина — не итоговая сумма, а то, что КАЖДЫЙ пункт плана
должен сам по себе начинаться у старта. Переделано на уровне построения
плана, а не проверки постфактум:
- Разминка и заминка теперь 100 м (2×50 одного упражнения), не 50 м.
- Брасс + спина объединены в один "круг" 100 м из двух РАЗНЫХ упражнений
  по 50 м каждое — рендерится как одна строка плана с двумя половинками
  (`item.combo` в `js/rulesEngine.js`, карточка `.plan-detail-combo` в
  `js/render.js`).
- Новое/предложенное упражнение с уменьшенным объёмом (50 м) теперь тоже
  всегда оформляется такой combo-парой с основным блоком кроля в роли
  заполнителя (`newItemCombo()`), а не остаётся одиночным пунктом.
- Итог: любая последовательность пунктов плана кратна 100 на каждой
  границе по построению, а не только суммарно. Подрезка при переполнении
  диапазона тоже обновлена под это (`js/rulesEngine.js`, `trimGuard`).
- Полная модель данных для пункта плана теперь: обычный `{code,
  volume_m}` ИЛИ combo `{combo:[{code,volume_m},{code,volume_m}]}`.
  `js/tabs/planTab.js` (`itemCodes`/`newItemCodes`) и
  `expandToRestSegments()` в `js/rulesEngine.js` обновлены под оба
  варианта.

**Разминка вернулась на шаг 1 (исправлено 2026-09-16, третий раунд).**
Второй раунд исправлений поставил разминку ПОСЛЕ блока с инвентарём,
чтобы точно не было ничего перед ним — но это было излишне строго:
правило требует не "нуль метров перед инвентарём", а "объём перед ним
кратен 100". Раз разминка уже стала 100 м (2×50), её можно (и нужно —
так интуитивно понятнее и совпадает с обычной практикой) вернуть на
первое место: 100 м разминки тоже кратно 100, инвентарь после неё
по-прежнему стартует у старта. Пользователь справедливо указал, что
"Разминка" как пункт №4 в списке читается странно — разминка ожидается
в начале. См. `js/rulesEngine.js`, порядок теперь: разминка → инвентарь
→ без инвентаря → заминка → резерв.

**Обязательный резерв мог оказаться после заминки (исправлено 2026-09-16).**
Пользователь включил в Настройках «Резерв — обязательный объём» и получил
план, где после заминки (последний пункт по правилам) шёл ещё один пункт
«Основной блок, кроль целиком» без всякой пометки — по сути, неотличимый
от резерва дубль. Причина: код добавлял обязательный резерв в самый конец
`items`, уже после того, как заминка была туда добавлена — нарушение
собственного правила PLAN_RULES.md "заминка всегда последний пункт".
Исправлено в `js/rulesEngine.js`: обязательный резерв теперь вставляется
перед заминкой (`items.splice` по индексу заминки), помечен `is_reserve:
true` и получает бейдж «резерв» и в кратком плане, и в подробностях
(`js/render.js`). Отдельный блок «Резерв» внизу страницы теперь
показывается только когда резерв опциональный ("если успевает") — когда
он обязательный, он уже виден в общей последовательности плана и второй
раз не дублируется.

**Чередование стабильных упражнений, не только drills (добавлено
2026-09-16).** Пользователь сказал, что готового чек-листа «исключить»
недостаточно — нужно настоящее разнообразие без ручного вмешательства
каждый раз, и явно назвал два упражнения: «Ноги с доской, брасс»
(`eq_kick_breast`) и «Спина, гребок с полной паузой у бедра»
(`ne_back_pause`) — раньше они включались в план БЕЗУСЛОВНО каждый раз
(только технические drills ротировались). Добавлено новое поле каталога
`always_include` (CATALOG_SCHEMA.md) — `false` у этих двух записей, у
всех остальных `true`. Когда `always_include: false`, упражнение
включается в план, только если его НЕ было в прошлой сохранённой
тренировке (та же логика, что уже работала для drills, обобщена и
вынесена в `rotationEligible()` в `js/rulesEngine.js`, применяется и к
блоку с инвентарём, и к базовым стилям без инвентаря). Уточнение для
пользователя: это **не случайный выбор кубиком**, а детерминированное
чередование по истории журнала — сохраняет требование "без AI, без RNG"
из этого документа. Поле можно переключать по месту в каталоге (колонка
"Чередование" в таблице) или при добавлении нового упражнения (чекбокс
в форме).

**Разнообразие оказалось слишком слабым — перешли на настоящую
случайность (2026-09-16, тот же день, следующая итерация).** После
добавления `always_include` (история-based чередование) пользователь
померил фактическую вариативность между двумя своими генерациями — всего
1 пункт из 10 (~10%) — и явно попросил 40-50%. Переделано: `js/rulesEngine.js`
теперь использует `Math.random()` (Fisher–Yates `shuffle()`) для выбора
ВНУТРИ уже разрешённого правилами набора — какие drills, включать ли
always_include:false упражнения, какое proposed-упражнение (если есть
слот) станет "новым" в этот раз (выбор идёт сразу по всем кандидатам —
инвентарь + без инвентаря — а не "чей блок в коде обрабатывается первым",
как было раньше, из-за чего почти всегда выигрывал `eq_sidekick`). Сами
ПРАВИЛА (кратность 100, порядок блоков, позиция у старта, лимит "не
больше 1 нового") остаются жёстко детерминированными — рандомизируется
только то, ЧТО из разрешённого попадёт в конкретный план. Проверено
скриптом (`test-variety.js` в scratchpad, не в репозитории): 8 генераций
подряд без сохранения в журнал — средняя разница 46% между планами, все
структурные инварианты держатся на каждом прогоне.

**Стилевой сет вместо простой пары (добавлено 2026-09-16, по трём
примерам тренировок SwimRocket, присланным пользователем).** В примерах
SwimRocket разнообразие строится не отдельными пунктами плана на каждый
стиль, а ОДНИМ сетом, который сам крутит 2-3 стиля по кругу ("9×50:
1.кроль 2.спина 3.брасс", "10×25 брасс+кроль"). Оказалось, что наш
`combo` (введён раньше для пары "брасс+спина") технически уже поддерживал
произвольное число половинок — рендер (`js/render.js`) и подсчёт объёма
(`itemVolume()` в `js/rulesEngine.js`) были написаны через `.map()`/
`.reduce()` по всему массиву, не завязаны на длину 2. Понадобилось только
написать сам билдер: пул стилей (брасс целиком + `ne_main_crawl` как
"кроль" + спина, если прошла по чередованию) перемешивается, число
отрезков случайно 2 или 4 (100 или 200м, всегда чётное — чтобы сет сам
оставался кратен 100), заполняется круговым проходом по перемешанному
пулу. Кроль (`ne_main_crawl`) сознательно используется повторно — он и
так уже есть отдельным гибким пунктом дальше в плане; в примерах
SwimRocket кроль тоже встречается по 2-3 раза за тренировку в разных
пунктах, это нормально. Название карточки в подробностях теперь
динамическое: "Круг Nм из двух упражнений" для 2 половинок, "Сет Nм —
чередование стилей (K×50м)" для большего числа.

статусом (не из seed) — имя обновилось, статус не затёрся. При любом
будущем переименовании упражнения — добавлять его в `NAME_MIGRATIONS`,
а не только в `exercise_library.json`/seed, иначе проблема повторится.
